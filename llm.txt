# betteroffice-meta-harness — for an agent picking this up

A differential rendering harness for BetterOffice's PowerPoint renderer. It renders a deck twice —
reference and candidate — diffs them per slide, clusters the differences into distinct renderer
defects, and turns each cluster into an upstream issue and a pull request.

This repo holds the method and the code. It holds no decks and no renders: the sample decks are
third-party copyrighted files, and renders of them stay on the machine that made them.

Read `harness.lock.toml` first. It says which component versions work together, and what has to be
installed.

## Setup

One command, from a fresh clone of this repo:

    git clone https://github.com/dsaad68/betteroffice-meta-harness
    cd betteroffice-meta-harness
    ./scripts/bootstrap.sh                                   # what it would do, changing nothing
    ./scripts/bootstrap.sh --install --fork https://github.com/<you>/betteroffice

It checks the tools, clones what is missing, installs the skills and agents where the agent runtime
looks for them, copies the scripts into the fork, and verifies nothing drifted. It is safe to
re-run: it skips what is in place, and warns before overwriting a skill or agent you have edited
locally rather than clobbering it. `--fork` takes a path if you already have a checkout.

What it sets up — three checkouts side by side:

    ~/GitHub/betteroffice-meta-harness   this repo: the method, the scripts, the agents
    ~/GitHub/fork/betteroffice           your fork of openooxml/betteroffice: the code under test
    ~/GitHub/pptx-pdf                    the reference renderer, built with `cargo build --release`

Tools, all checked by `scripts/install_tools.sh` (which `bootstrap.sh` calls, and which reads its
required versions out of `harness.lock.toml` so the two cannot drift):

    python >= 3.11   uv >= 0.5   gh >= 2.0 (authenticated)   a Rust toolchain
    wt >= 0.76       worktrunk, for per-agent worktrees
    sem >= 0.24      optional — entity-level impact analysis; nothing fails without it
    pptx-pdf         the reference renderer. Not a package: a checkout built in place, at the
                     path common.py expects. Nothing can be compared without it.

Add `bun` if you touch the TypeScript renderer. `scripts/common.py` holds the paths — change them
there, not in each script.

**You supply the decks.** This repo carries none and never will: they are third-party copyrighted
files, and renders of them stay on the machine that made them. `scripts/add_deck.py` registers one.

To install by hand instead, or to see exactly what bootstrap does, run it without `--install` — the
plan it prints is the whole of it.

## Running the scripts

**Every script is a self-contained uv script.** The PEP 723 header names its own dependencies, so
there is no shared virtualenv to create, activate or keep in sync — uv resolves each script's
dependencies on first run and caches them.

    ./scripts/pipeline.py deck.pptx --id my-deck
    uv run --script scripts/pipeline.py deck.pptx --id my-deck   # same thing

Do not run them with a bare `python`: the dependencies will not be there. If one script spawns
another it uses `uv run --script` for the same reason — `sys.executable` would hand the child the
parent's environment, which does not carry what the child declared.

All of them take `--help`. They use click, so options behave the way you expect.

### The candidate renderer

`betteroffice_pptx` is not on PyPI: it is a Rust extension built from the fork by
`scripts/setup_worktree.sh`. `render_bo.py` and `verify_fix.py` need it, and `common.ensure_binding()`
finds it — first `BETTEROFFICE_BINDING`, then the local build in the working repo.

uv can build it too. `[tool.uv.sources]` is honoured in PEP 723 inline metadata (verified, though
the dependency docs only describe `pyproject.toml`), so either of these resolves it:

    # /// script
    # dependencies = ["betteroffice-pptx"]
    #
    # [tool.uv.sources]
    # betteroffice-pptx = { git = "https://github.com/openooxml/betteroffice", branch = "main", subdirectory = "bindings/python-pptx" }
    # ///

    # or, against a checkout you already have:
    # betteroffice-pptx = { path = "../betteroffice/bindings/python-pptx", editable = true }

Or with no edit to the script at all:

    uv run --with "betteroffice-pptx @ git+https://github.com/openooxml/betteroffice@<rev>#subdirectory=bindings/python-pptx" \
           --script scripts/render_bo.py my-deck

**The harness does not pin it, deliberately.** The engine is the thing being measured: it changes
per worktree and per run, which is the whole point of `verify_fix.py --engine`. A source fixed in
the script header cannot express "whichever worktree I am comparing right now". Use the git form
when you want a known revision — a one-off measurement against upstream, or reproducing someone
else's number — and the built local engine the rest of the time.

## The two renderers

**Reference** — `pptx-pdf`, a CLI driving an embedded LibreOffice to PNG at a chosen DPI.

**Candidate** — BetterOffice's own `render_png`. It did not exist when this work started; it was
added upstream as openooxml/betteroffice#264 precisely so the renderer could be measured. That has
merged, so `crates/pptx-raster` is on `main` and a fix worktree cut from `main` can render.

Both render at 96 dpi with Liberation, Carlito and Caladea aliased to the metric-compatible
Microsoft families, so a difference means layout, not fonts.

## The two loops

**Finding defects** — skill `render-harness`:
register and render a deck, fan out one `slide-comparator` per slide, cluster with
`failure-taxonomist`, then one `issue-investigator` per cluster writing `report.md` and
`possible-solution.md`.

**Fixing them** — skill `fix-loop`:
build a dependency-ordered `ORDER.toml`, fan out `issue-fixer` agents (up to three), then file and
push serially. Agents cut their own worktrees with `wt` and never call `gh`, never push, never
rebase — parallel agents that publish will conflict with each other and duplicate analysis when two
clusters share a cause.

Two habits the loop depends on, both learned the hard way. **Write a filing back into `ORDER.toml`
as the last step of each entry**, not batched at the end — the plan drifted ten entries behind
GitHub twice, and `order.py ready` then hides work that is already unblocked. And **`wt remove` a
branch's worktree once its pull request merges**: each carries 15–20 GB of build cache, forty
clusters fill a disk, and the failure arrives as a linker error in an unrelated crate rather than
as "out of space".

`ORDER.toml` has one writer, the dispatching session. It carries the whole backlog — every
investigated cluster, `todo` until someone takes it — with each entry's report, solution and evidence
paths in its metadata. `scripts/order.py` queries it (`backlog`, `ready`, `plan`, `deps`, `report`,
`check`) and renders the merge-order issue body. `TODO.md` is
where agents write as they work. `LEARNING.md` is appended to across runs.

Do not confuse the two TOML files. `harness.lock.toml` locks the harness itself: which skill, agent
and script versions work together. `ORDER.toml` is the work: which fixes and features depend on
which. One is generated fact, the other is hand-authored intent.

## Things that will mislead you

**The per-pixel percentage is triage, not a score.** A correct fix can raise it: text drawn at its
proper size diverges more from a reference whose line breaking differs than the wrong-sized text
did. A fix landing before its dependency can raise it. And a small correct fix barely moves it —
removing twelve stray digits from a chart is about 123 pixels on a 1280×720 slide. Judge against the
issue's own verification section, and look at the render.

**Ask what else a change touches before scoping it.** The pptx crates share `ooxml-drawingml`,
`ooxml-text` and `opc` with docx and xlsx, so a fix that looks local often is not: `sem impact
arrow --file crates/ooxml-drawingml/src/geometry.rs` names a dependent in `crates/docx-parse`. A
preset-geometry fix shipped as a pptx change was a docx change too. The `sem` skill covers it;
"nothing else calls this" is a `grep` result until something checks.

**An investigation report is a strong prior, not a fact.** They have been wrong: one proposed a
field on a struct the writer never sees; another missed that lifting a clip breaks hit testing.
Verify the central claim against the code before building on it.

**Measure against the right baseline.** If your branch stacks on an unmerged fix, the baseline needs
that fix too, or you will credit its effect to yours.

**`wt` hooks run in the background.** `wt switch --create … --yes` returns before the worktree is
provisioned. Confirm the binding resolves to your worktree and exposes `render_png` before you
trust a measurement.

**Evidence must be publishable.** Only decks whose slides carry placeholder content. Never a
third-party presentation, never a slide showing a person's name or contact details.
